# Python / Java 需求种子库

拼装需求用的素材。每个种子给出：**业务背景 + 需求要点 + 可检验的验收点**。使用时结合学习者项目现状改写，不要原样照搬。

种子分两类：
- **业务流程种子**（P1-P4 / J1-J4）：围绕具体业务场景，需要学习者理解业务动机
- **工程能力种子**（P5-P8 / J5-J8）：围绕代码工程短板，伪装成客户业务诉求让学习者自己发现

## Python 侧种子

### P1 · Web 后端（FastAPI / Flask / Django）· 业务流程
- 背景：接口被外部客户调用，最近投诉多。
- 需求要点：新增一个资源端点（如批量导出 / 批量导入 / 状态流转）。
- 验收点：参数校验（空值、超长、非法枚举）；业务规则拦截（如仅允许特定状态流转）；异常返回统一格式而非 500 裸堆栈。

### P2 · 数据处理脚本 / 报表 · 业务流程
- 背景：运营每天手动跑脚本出报表，出错过几次。
- 需求要点：给现有处理流程加「数据质量检查」前置步骤。
- 验收点：空文件 / 脏数据行有明确报错；重复运行结果一致（幂等）；输出带统计摘要。

### P3 · CLI 工具 · 业务流程
- 背景：内部工具，同事反馈参数记不住、出错难排查。
- 需求要点：加一个子命令 + 参数校验 + 错误信息友好化。
- 验收点：`--help` 说明清晰；非法参数给出可操作提示；中途失败有退出码和原因。

### P4 · 爬虫 / 数据采集 · 业务流程
- 背景：采集量变大，老是被对方限流。
- 需求要点：加限速、重试、断点续采。
- 验收点：请求间隔可控；失败自动重试有限次；中断后续跑不重复已采数据。

### P5 · 测试补全 · 工程能力
- 背景：客户验收时发现关键路径没单测，最近一次回归引入 bug 没人发现。
- 需求要点：给现有核心模块补单元测试，覆盖主流程 + 至少 2 个边界。
- 验收点：覆盖核心路径；至少 2 个边界案例（空 / 非法 / 极值）；测试可独立运行不依赖外部服务。
- 模糊点：覆盖率目标由学习者自定（≥60% / ≥80%），客户只关心"核心路径必覆盖"。

### P6 · 数据迁移 · 工程能力
- 背景：业务侧要求把历史脏数据迁到新格式，运维抱怨手动迁了三次还有遗漏。
- 需求要点：写一次性迁移脚本，处理存量数据格式不一致。
- 验收点：迁移前后数据条数一致；迁移可重复运行（幂等，已迁数据不再迁）；迁移失败有日志可定位到具体行。
- 模糊点：脏数据是跳过还是修复，由学习者决策。

### P7 · 日志可观测性 · 工程能力
- 背景：线上出过一次故障，排查时发现日志只有 print，没法定位是哪条请求。
- 需求要点：给关键路径加结构化日志，每条带请求 ID / 用户 ID。
- 验收点：日志含可关联的 trace ID；同一请求的日志能串起来；敏感信息（密码、token）不出现在日志里。
- 模糊点：trace ID 是请求级还是会话级，由学习者决策。

### P8 · 配置外部化 · 工程能力
- 背景：客户每隔几周就要改一个魔法值（限流阈值、缓存 TTL），每次都改代码发版太重。
- 需求要点：把硬编码配置挪到外部配置文件 / 环境变量。
- 验收点：核心配置项不在代码里；运行时可通过环境变量覆盖；缺配置时给明确报错而非用 None。
- 模糊点：配置格式（yaml / env / toml）由学习者选，客户不指定。

## Java 侧种子

### J1 · Spring Boot 后端 · 业务流程
- 背景：订单 / 业务接口在高峰期偶发错误，客户投诉重复提交。
- 需求要点：给核心写接口加幂等处理 + 参数校验。
- 验收点：重复提交只生效一次；非法请求返回 4xx 业务错误而非 500；错误信息面向调用方可理解。

### J2 · 后台管理系统 · 业务流程
- 背景：管理员抱怨列表页慢、没法筛选。
- 需求要点：给列表查询加分页 + 条件筛选 + 排序，替换当前全量查询。
- 验收点：大数据量下响应可控；组合筛选结果正确；默认排序稳定（无随机乱序）。

### J3 · 命令行 / 批处理工具 · 业务流程
- 背景：批处理任务跑批慢，且中途失败要人工盯。
- 需求要点：任务拆分（分片处理）+ 失败记录与恢复。
- 验收点：大文件可分片跑完；某片失败不影响其他片；重跑只处理失败部分。

### J4 · 并发改造 · 业务流程
- 背景：单线程处理太慢，想利用多核。
- 需求要点：把现有顺序处理改为线程池并发，并保证结果不丢不乱。
- 验收点：并发后结果与顺序处理一致；有明确的线程池边界与关闭逻辑；异常任务不拖垮整体。

### J5 · Spring Security 鉴权 · 工程能力
- 背景：客户要做安全审计，发现部分接口谁都能调。
- 需求要点：给现有接口加角色校验，区分管理员 / 普通用户可访问的资源。
- 验收点：未登录访问受保护接口返回 401 而非 500；无权限访问返回 403；公开接口不受影响。
- 模糊点：角色枚举的具体值由学习者定，客户只关心"至少两档"。

### J6 · MyBatis / JPA 拦截器 · 工程能力
- 背景：客户要求所有写操作都要有审计日志，但又不想每个接口都改。
- 需求要点：用拦截器 / AOP 统一给写操作加审计字段（操作人 / 时间）。
- 验收点：所有写操作自动带审计字段；不需要每个 Service 手动 set；读操作不受影响。
- 模糊点：操作人从哪个上下文取（线程局部 / 注入），由学习者决策。

### J7 · 配置中心化 · 工程能力
- 背景：多环境部署时配置散在各处，发版经常配错。
- 需求要点：用 Spring Profiles / 外部配置统一管理多环境配置。
- 验收点：同一份代码在 dev / prod 下行为不同；切换环境不改代码；缺关键配置启动报错而非用默认值。
- 模糊点：是否引入配置中心（Nacos / Apollo）由学习者决策，本地 profile 也算合规。

### J8 · 全局异常处理 · 工程能力
- 背景：客户接入 API 后抱怨错误响应格式不一致，有的 500 裸堆栈有的 JSON。
- 需求要点：用 `@ControllerAdvice` 统一异常处理，所有接口错误响应格式一致。
- 验收点：业务异常返回结构化错误（code / message）；未知异常返回友好提示而非堆栈；HTTP 状态码与业务码语义一致。
- 模糊点：错误码规范由学习者定，客户只关心"同类型错误响应一致"。

## 模糊点注入建议

| 种子 | 可留的模糊点（供学习者澄清或决策） |
|---|---|
| P1 / J1 | "非法请求"具体指哪些情况？是否需要限流？ |
| P2 | 脏数据是跳过还是整批失败？ |
| P3 | 错误信息格式有无既有规范？ |
| P4 | 限速值由谁定、是否可配置？ |
| P5 | 覆盖率目标？是否需要 mock 外部依赖？ |
| P6 | 脏数据跳过还是修复？是否需要 dry-run 模式？ |
| P7 | trace ID 是请求级还是会话级？日志输出到哪？ |
| P8 | 配置格式（yaml / env / toml）？热更新是否需要？ |
| J2 | 筛选条件组合是 AND 还是允许 OR？默认排序字段？ |
| J3 | 分片大小？失败后重跑粒度？ |
| J4 | 并发度上限？顺序是否必须保证？ |
| J5 | 角色枚举具体值？是否需要动态加角色？ |
| J6 | 操作人来源（ThreadLocal / 注入）？审计日志存哪？ |
| J7 | 是否引入配置中心？多环境切换方式？ |
| J8 | 错误码规范？是否对调用方暴露内部错误码？ |

规则：每轮只注入 1-2 个模糊点；模糊点必须能被业务澄清或合理决策解决，不许留"死结"。
