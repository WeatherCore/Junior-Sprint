# 需求生成方法论

阶段 1 的权威参考。目标是：基于学习者项目的真实现状，生成**像真实客户会提**的需求，而不是凭空编造的练习册习题。

## 需求来源三选一

1. **项目现状派生（首选）**：从阶段 0 侦察到的模块、数据模型、已有功能出发，提一个「增量」需求。例：项目有 `User` 模型和登录接口 → 客户提「加个忘记密码 / 用户封禁」。
2. **项目短板暴露**：代码里明显的薄弱点（无校验、无异常处理、耦合重）包装成客户业务诉求，让学习者自己发现并解决。例：客户抱怨「下单偶尔会重复扣款」→ 对应幂等性问题。
3. **业务扩展想象**：基于项目定位想象下一个业务版本。例：个人记账工具 → 「加预算管理」。

默认用方式 1；每次需求至少 80% 的改动面落在项目已有模块上，不引入全新领域知识。

## L1 / L2 / L3 难度定义

| 档位 | 典型改动 | 涉及文件 | 独立完成参考时长 | 训练重点 |
|---|---|---|---|---|
| **L1 单点改动** | 改一个方法逻辑、加一个字段、补一个边界判断、修一个 bug 场景 | 1-2 个文件 | 30-90 分钟 | 需求理解、最小改动、边界思考 |
| **L2 新功能**（默认） | 新增一个完整功能：一个端点 + 数据层 + 展示 / CLI 命令；或一个业务流程 | 3-8 个文件 | 2-4 小时 | 问题拆解、跨层协作、自测 |
| **L3 系统重构** | 模块拆分、引入抽象层、性能优化、迁移重构、并发改造 | 5-10+ 个文件 | 半天以上 | 架构判断、权衡取舍、回归保障 |

难度不只由代码量决定，还由**模糊度**决定：L3 需求故意留更大的业务空白，让学习者自己澄清或决策。

## 需求设计五原则

1. **业务真实**：给业务背景和动机（客户为什么现在要这个），不写技术方案。
2. **复用现状**：需求必须能落在学习者现有代码上，可引用已有模块 / 字段 / 接口。
3. **验收可检验**：验收标准写成业务规则和边界案例（"金额为 0 时拒绝"、"重复提交只生效一次"），不写"请写单测"这类工程指示。
4. **留 1-2 个模糊点**：真实需求总有歧义。故意留的模糊点应是学习者通过提问能澄清的（客户会回答业务层面），或是需要学习者做决策的（客户会给决策空间）。不要留到无法动手的模糊度。
5. **一次一个主线**：一轮 Sprint 只围绕一个业务目标，避免需求堆叠。

## 生成流程（在阶段 0 侦察完成后）

1. 回顾侦察结果：技术栈、模块清单、数据模型、已有功能。
2. **跨轮成长基线读取**：若学习者项目根目录存在 `SPRINT-RETRO.md`，先读上轮复盘，参考"自主排错"分数调整本轮难度默认值（见下方 AI 主动换档）。
3. 选难度档（默认 L2，若有上轮基线则按主动换档规则调整），选来源方式（默认方式 1）。
4. 用 `references/demand-seeds.md` 的种子拼装出贴合项目现状的需求骨架。
5. 填入 `assets/templates/demand-card.md`，检查三要素齐全（业务背景 / 要什么 / 验收标准）。
6. 发布时**保持客户口吻**：不知道"文件"、"接口"、"数据库"这些词存在，只谈业务（除非学习者已进入指导模式并主动问实现细节）。
7. 复述确认环节顺带收集学习者**交付估时**（"预计多久能交？"），记录备用——复盘对比"估时 vs 实际"偏差（见 `references/acceptance-review.md`）。

## 换档规则

### 学习者主动换档

- 学习者觉得太难 → 降一档，或保留难度但缩小范围（砍掉一个验收点）。
- 学习者觉得太简单 → 升一档；若已在 L3，则叠加约束（"必须兼容旧数据"、"不能改现有接口签名"）。
- 换档后重新发需求卡，不必重新侦察。

### AI 主动换档（基于上轮复盘）

AI 在阶段 0 读取 `SPRINT-RETRO.md` 后，按下表对"自主排错"维度主动建议换档：

| 上轮自主排错分数 | 本轮默认档 | 本轮重点训练 |
|---|---|---|
| ≥4 | 升一档（L1→L2 / L2→L3 / L3→L3+约束） | 挑战架构判断 / 权衡 |
| =3 | 保持当前档 | 巩固既有能力 |
| ≤2 | 降一档（L2→L1 / L3→L2 / L1→L1 缩范围） | 强化需求理解 + 边界思考 |
| 首轮（无基线） | L2 默认 | 全维度建立基线 |

主动换档规则：

1. AI **明确告知**学习者"基于你上轮自主排错 X 分，本轮建议 Y 档，理由是 Z"。
2. 学习者可拒绝——保留选择权，AI 不强制。
3. 若学习者拒绝且分数 ≤2，AI 在复盘时仍按"自主排错"维度追踪，连续 3 轮无提升则再次提议降档。
4. 主动换档仅参考"自主排错"维度——其他维度（需求理解、拆解、工程习惯、沟通）的短板通过"重点训练维度"在复盘报告里标注，不直接换档，避免难度抖动。

### 重点训练维度传递

每轮复盘报告末尾标注"建议下轮重点训练维度"，下一轮 AI 在阶段 1 出需求时优先选能训练该维度的种子（如上轮短板是"边界思考"，本轮优先选含明确边界案例的种子）。

## 需求变更剧情（可选事件，L2 / L3）

真实职场对新人冲击最大的场景之一是 mid-sprint 客户改需求。一轮 Sprint 可选触发**至多一次**"客户变更"事件，训练范围确认与排期谈判：

- **触发时机**：阶段 2 攻坚过半（学习者已汇报实质进展）时，由客户身份插入。
- **变更幅度**：改一条验收标准，或追加一个小需求点；不推翻主线，不超出原范围一小步（守住"一次一个主线"原则）。
- **下达方式**：纯业务语言说清变更与业务理由（"老板临时要的""客户侧又提了一嘴"），口头下达即可，不重新发需求卡。
- **观察点（记入复盘"沟通"维度）**：学习者是否 (1) 与客户确认新范围与影响面；(2) 调整自己的拆解与估时；(3) 必要时敢于谈判（"这个能不能放下期""先交原范围"）——敢谈是加分，不是冒犯。
- **兜底**：学习者明显被变更打懵时，客户主动给一句范围澄清；学习者闷头照单全收时，复盘指出"真实团队里不确认范围的变更最容易做偏"。
- 若变更实质改变交付物（超过一个小验收点），按"学习者主动换档"流程重新发需求卡并重跑 `assets/scripts/check_demand_card.py`。
